# Bullseye (Tauri tray app, Windows only)

Blocks sites (closes matching Chromium-browser tabs), closes programs by exe name, and closes Obsidian when it shows web content. The user defines three kinds of things, each a list of its own with its own page: **block lists** (what to block: sites, allowed sites, programs, and the enforcers that act on them), **conditions** (when: named, of a type: a weekly schedule, a flash drive that is not connected, or a combination of two or more of those, any one of them or all of them, never of other combinations; "always" is built in), and **blocks** (what is started: one or more block lists, a condition or always, at most one **allowance**, set on the block itself in its editor, never a list or page of its own (what lets a block go quiet for a while: a **budget**, an allowed time of use for the block as a whole or for each item of it, given back never, every so long (any duration, counted from the block's start or on the clock from midnight, as a Pomodoro is; the user dropped the fixed hour / day / week) or each time the block's condition turns on; or a **Pomodoro**, a fixed cycle of blocked time then allowed time, counted from the block's start or from midnight on the clock; see `allowance.rs`), and a **lock**: none, a duration, until a date and time, until Windows restarts, a condition lock (cannot be stopped while a chosen condition is active; with the block's own condition that is "locked while active"; a flash drive condition is active while the drive is not connected, so the drive is the key) a delay (stopping is asked for, counts down on internet time and can be aborted, like the global unlock; once the wait is over the block can be stopped), a custom text (cannot be stopped until its text is typed in exactly, as the window shows it above an input that refuses pasting) or a password, kept only as a salted hash). Each block is started and stopped on its own, and several can run at once. A running block that is **locked** cannot be changed, and the block lists and conditions it uses can only be made stricter; one that is not locked can be changed (name, block lists, condition; never its lock, which is only chosen for the next start), and so can what it uses, and the change goes to the running block. Deleting follows the same rule: refused while a locked block is involved, otherwise it goes and the running blocks follow (a block left without a block list is deleted and so ends; one that lost its condition is always active; one that lost its lock condition has no lock now). Deleting a block list or condition takes it out of the blocks that use it (none of which may be locked): a block left without a block list is deleted, one that loses its condition is always active, one that loses its lock condition has no lock (`Library::fallout`, which the delete question spells out). While its condition is not active a running block still runs (and stays locked) but enforces nothing. Definitions and running blocks are held by a **SYSTEM Windows service**; the tray app does the closing. This file is the project's documentation for developers; `CLI.md` is the command line's.

- `src/` – the frontend, built with the **Carbon design system** (see "Design system" below), with no build step: `index.html` (the markup), `app.css` (the page's own layout, in Carbon tokens) and the ES modules in `src/js`: `main.js` (start-up, the router, the tabs, Settings), `core.js` (commands, texts, the status, `ask`, notices), `kinds.js` (`KINDS`), `forms.js` (`LISTS`, `SECTIONS`, the three forms and `weekEditor`), `locks.js` (`LOCKS`), `tiles.js` (the pages of tiles, start / stop, delete), `editor.js` (the editor and its breadcrumb) and `detour.js` (a block list or condition made from a block). Pages by URL hash, reached from the tabs (Blocks, Block lists, Conditions, Settings): `#/`, `#/lists`, `#/conditions` show each kind as tiles; `/new` and `/edit/<id>` under each (`#/new`, `#/lists/edit/<id>`, …) open its editor (left by Cancel or Save); `#/settings` unlocking (and its delay), and Export / Import of everything defined (to move to another computer). The three kinds are described once in `KINDS` (title, paths, commands, `held`, a form built by `blockForm` / `listForm` / `conditionForm`), and pages, tiles and the editor are generic over it. The block list editor and summaries come from `LISTS` and `SECTIONS` (enforcers grouped with the lists they use); a block's lock is set **on its tile**, next to Start (a select from `LOCKS`, saved with the block as it is chosen; a method with settings asks for them first); a condition's editor is `conditionForm`: a name, a type select, and for a weekly schedule `weekEditor`, a week grid of half hours to drag over (a new one starts empty), with the schedule written out under it (`describe_schedule`), or for a flash drive `drivePicker`, a select of the drives connected now (`connected_drives`, scanned when the editor opens and on "Scan again"; the drive it was set to stays in the list while away). The page blocks WebView2's right-click menu (Back, Refresh, …) except in text fields. Every time shown (time left, a lock's length, the unlock delay, until a condition or lock changes) is written by `duration::countdown`: the largest unit and the one below it, never seconds from an hour on (`1 day and 2 hours`, `13 hours and 7 minutes`, `5 minutes and 3 seconds`, `42 seconds`). Window texts are GUI labels, short with little punctuation, a countdown reading "for the next {time}" (`Inactive for the next 13 hours and 7 minutes`, `No active lock`). **The page has no logic of its own for what the backend knows**: the words come from Rust (`Running::remaining_words` / `condition_change_words` in the status, the local commands `describe_duration`, `describe_schedule`, `describe_until` and `deletion_fallout` (what deleting a block list or condition does to its blocks, `Library::fallout`), cached by `described()` where they are shown on tiles), and every action is a command that the CLI sends as the same `Request` through the same `client::Remote`
- `src/strings.js` – **every text the window shows**, in one file for fine-tuning the copy (`window.STRINGS`, nested by page). The page looks them up with `t("path", {placeholders})` (`{n}` picks `one` / `other`); the markup's static texts use `data-t="path"` and `data-t-<attribute>="path"` (`applyStrings`). A new visible text goes there, never inline. Texts from Rust (times in words, schedules, the service's errors) are not in it, so the window and the CLI say the same
- `app-icon.svg` – the app icon: an archery target of five bands of equal width (white, black, blue, red, yellow centre), the source of everything else: `app-icon.png` (1024 px, rendered from it in a browser) and `src-tauri/icons/*` (`npx tauri icon app-icon.png`). Change the SVG, then regenerate both. The icon is not shown in the window's header (the user found it ugly there). It fills its square edge to edge
- `src/vendor/` – Carbon, built by `npm run vendor` (`scripts/vendor-carbon.mjs` from `scripts/carbon/entry.js` and `carbon.scss`) and committed; never edit by hand
- `src-tauri/src/lib.rs` – the shared library: modules, entry modes (`--service`, `--install`, `--uninstall`, otherwise the app), tray, and the page's commands: `block_status`, `save_block` / `delete_block`, `save_list` / `delete_list`, `save_condition` / `delete_condition`, `duplicate` (any of the three kinds), `start_block` / `stop_block` and `unlock_all` forward to the service, `describe_schedule` / `describe_duration` / `describe_until` / `deletion_fallout` are local, and so are `export_settings` / `open_settings` (the Save and Open dialogs, `tauri-plugin-dialog` from Rust, so the page needs no plugin permissions; the app writes and reads the file, as the user) with `import_settings` sending what it read to the service. `main.rs` is the tray exe (`bullseye.exe`, GUI subsystem), `bin/bullseye-cli.rs` the console exe of the CLI. The library is `bullseye_core` (a library and a binary of the same name collide on Windows)
- `src-tauri/src/cli.rs` + `CLI.md` – the command line, `bullseye-cli.exe`: everything the window can do (`status`, `show`, `new`, `edit`, `delete`, `duplicate`, `start` (with a lock option, like the tile), `stop`, `list show|new|edit|delete|duplicate`, `condition show|new|edit|delete|duplicate|check`, `drives`, `list apps`, `export`, `import`, `unlock`), through the same `client::Remote`. **Keep it level with the window**: a command in `generate_handler!` needs an entry in `cli::GUI_COMMANDS`, a CLI command, a line in the help and in `CLI.md`; a test fails otherwise
- `src-tauri/src/ui.rs` – the window: none at startup, made on a tray click (shown once the page has drawn), its X only hides it, destroyed after 5 minutes hidden (the web view is almost all of the app's memory)
- `src-tauri/src/service.rs` – the running SYSTEM service (service manager, start-up, data folder lock-down); `handler.rs` – what it does with each request (the same code over the pipe and, in debug builds, inside the app); `registration.rs` – installing, locking down (SDDL), starting and removing it
- `src-tauri/src/pipe.rs`, `proto.rs`, `client.rs` – the named pipe `\\.\pipe\bullseye`: server, messages, and the app's side (keeps the last policy in memory; `Remote::local` is the in-process variant)
- `src-tauri/src/definitions.rs` – the `Library`: `BlockList`s, `Condition`s (id, name and a `condition::Rule` flattened in as `type` and its fields) and blocks (`Definition`: id, name, list ids, condition id or `None` for always, `lock`), kept in `%ProgramData%\bullseye\blocks.json`. `resolve` looks a block's parts up for starting; `delete_list` / `delete_condition` take the item out of the blocks that use it (`Library::fallout`); `duplicate` copies any of the three as a new id the client gives, named `Work (2)` (`copy_name`: the next number free), a block with its lock, a password's hash included. The settings file of Export / Import (`SettingsFile`: `bullseye_settings: 1` and the library; `write_settings`, `read_settings`) has password locks with their hash, never the password (the user chose this; a short password could be guessed at from the file offline, so the file is to be kept private; `Request::Export` gives the app the whole library, as the status has the hashes left out), so they import with their hash (a block whose file has none comes without a lock: `Contents::unlocked` says which first); Store apps the file has that this computer has not installed are left out (`Library::without_missing_apps`, asked by the app or the CLI, as the user, before sending: the service runs as SYSTEM and cannot ask for the user's apps; a family name is one exact package, so the same app as another package, such as a sideloaded MSIX `Claude_pzs8sxrjxfjjc` against the Store's `AnthropicPBC.Claude_fnn82j28hfe8t`, is not a match, and nothing is matched by name: the user chose this), and the question before importing and the notice after it say which; `Definitions::replace` checks everything as saving would and replaces it all, refused while any block is locked (`handler::import`; blocks that run unlocked end with it). A password lock's password is hashed when saved and never sent back (`Library::redacted`). Each block also keeps the last settings of every other lock method it has had (`kept_locks`, merged by `save_block`; a client's are ignored; a kept condition lock is no use of that condition, and deleting the condition removes it from every block's `kept_locks`), so a method chosen again starts from them, a password as its kept hash. Only today's format is read: Bullseye is installed on clean machines only, with no update path and no migration code
- `src-tauri/src/handler.rs` also holds the sharing rule (under one lock with `start`): deleting a block list, condition or block (`delete_shared`, `delete_block`) is refused while a locked block is involved, else the running blocks follow what is left (a running block that is deleted is stopped first); `edit_block` saves a running block that is not locked right now (not its lock: that must be as defined; at least one block list), `edit_shared` its lists and conditions, and both give the running block the result (`refresh_running`, `Blocklist::refresh`, which also renames it). Saving a block list or condition that running blocks use is `edit_shared`: if none of them is locked right now (`Blocklist::locked_ids`) it is free, and if one is, it must be stricter: `BlockList::tightened_by` (more entries to block, fewer allowed, enforcers only turned on, compared as `Lists::entries` reads them: so replacing `youtube.com` by `*` is refused, though stricter) and `Rule::tightened_by` (a schedule keeping every time it has; a flash drive staying the same drive; used both as a block's condition and as its lock condition, where more active time is stricter too). A block's own allowance follows the same rule in `edit_block`: free while it is not locked, and while it is, only stricter (`allowance::tightened`: none is stricter than any, terms by `Terms::tightened_by`), so the block editor leaves the allowance open (with the name) on a locked block. The change then goes to every running block that uses it (`Blocklist::refresh`: lists, condition, allowance (what is used stays, unless its scope changed) and lock condition's rule; the lock itself, zone and start stay). The window leaves such an editor enabled, with a notice, and shows the service's refusal; its example entries (placeholders) are hidden while it is limited or read-only, as they read as entries
- `src-tauri/src/block.rs` – the running blocks, keyed by definition id: one `Part` per block list (each with its own enforcers and allowed sites), condition (a `Rule`), time zone and its lock (`RunLock`, one variant per lock: when it ends, its lock condition's rule, the start of Windows it waits out, a password's hash; also how `state.json` keeps it; `StartLock` is what starting asks for); locks and schedules are enforced here, never in the UI. `Active` is what the app enforces: every part of every running block that its condition has active. `is_running()` is "any block exists" (keeps the app alive, refuses updates), also outside its condition; `locked()` says why one cannot be stopped now (and refuses uninstalling)
- `src-tauri/src/allowance.rs` – allowances. `Terms` (tagged by `type`: `budget` with `allowed` (`30m`), `scope` `total` / `each` and `reset` `never` / `every` (with `every`, a duration, and `anchor` `start` / `clock`) / `condition`; `pomodoro` with `blocked`, `allowed` and `anchor` `start` / `clock`) is a block's `Definition::allowance` (`None`: none), set on the block like its lock, never a kind of its own (the user chose this: there was an Allowances page, and it was dropped); saved, duplicated, exported and imported with the block, checked by `save_block` / `replace`. `Terms::checked` (durations that read and are not zero; a cycle at most 24 hours, and on the clock one that fits a day evenly), `Terms::tightened_by` and `tightened` (what a **locked** block's allowance may change by (`handler::edit_block`): none is always stricter, giving one never is; a budget gets shorter or resets less often (every so long only longer and counted from the same point, or never; by condition only stays), never another scope or type; a cycle cannot change at all, as any change moves where it is in the cycle), `Terms::describe` and `label` (the words in full, for the editor and the CLI, and short for the tile's line, `Allowed 30 minutes a day`, as other tile lines are short: the local command `describe_allowance` gives both). A per-item budget's item is **one entry as typed**: a wildcard entry (`*.reddit.com`, `steam*.exe`, a lone `*`) is one item with one budget for all it matches; a page matched by two entries counts against both and is closed once either is used up; the key is the entry's text, so an entry typed anew starts afresh, and the same entry in two block lists of a block is one item. A running block holds a `Run` (terms, `used` per key in milliseconds, the `period` it belongs to (`None` until known, so new terms never give the time back early: `retermed`), `was_active` for the reset by condition, `started`; kept in `state.json` as `Saved::allowance`, written with the checkpoint every minute). **What is let through is decided by the service, never the app**: while a cycle allows, `Block::enforced` gives no part at all (Obsidian's enforcer too); with a budget that has time, the part's lists are not enforced but handed over as `block::Free` (a total budget: the whole part as one item with key `""`; each: every entry on its own, key `site:` / `program:` / `app:` / `title:` and the entry, see `item_keys`) in `Policy::free`, with the part's always-allowed sites as exceptions, and what is used up is enforced again (`RunPart::remainder` keeps the lists without the items still free, parsed once). Obsidian's web viewer enforcer has no list to watch, so it stays enforced with a budget. **Use is what the app sees**: `Active::judge` (behind every `blocks_page` / `blocks_app_window` / `blocks_firefox_page` / `blocks_program` / `blocks_store_app` / `blocks_title`) notes a free item that matches and is not closed into `Active::used` (`block::Usage`: a page shown in a tab, so never a background tab; a window; a running program); `client::Remote::active` sends it as `Request::Report` just before each `Policy` request, and the service counts it (`Blocklist::charge`) for the time since it last answered a policy request (`polled`, at most `MAX_GAP` = 5 s), only for keys the block counts and only while its condition is active; anyone may send a report, but it only ever counts against a block. Resets are made lazily by `Run::advance`, called whenever the blocks are looked at (a clock reset from the zone's local time: `into_period`; a reset by condition when the block's condition is seen turning on, so it needs the app asking, as it does). **A new kind of allowance** is a variant of `Terms` with what it means in `Run` / `Block::enforced`, fields in the block editor's `allowanceSection` (`forms.js`), and an option of the CLI's `new|edit --allowance`.
- `src-tauri/src/condition.rs` – `Rule`, what a condition is, tagged by `type`: `schedule` (a `Week`: active at its times), `flash_drive` (`serial`, `drive`: active while that drive is **not** connected) and `combined` (`mode` `any` / `all`, `members`: ids of other, non-combined conditions, at least two, once each); `active(zone, now)` and `next_change` (for a combination the next time the *combination* flips, found by stepping through its members' changes, at most 64 steps). A combination in a definition holds only ids; `Library::rule_of` gives a running block `rules` too, copies of its members' rules, in order, so the block runs by what they were at its start (`Condition::checked` strips `rules` from what is stored). A combination is used anywhere a condition is: a block's condition, a condition lock. Rules while locked: `Library::usages` says how a block uses a condition (`Via`: directly, in an "any", in an "all"); a condition in an "any" or used directly follows `Rule::tightened_by` (more active); one in an "all" cannot change at all (more active there is not more in the combination); a combination itself gets more active by `any` gaining members, `all` losing them or becoming `any`. Deleting a condition takes it out of the combinations it is in, and a combination left with one condition is deleted too, with the usual effect on its blocks (`Library::going_with`, `fallout`: `shrinks` and `removed`; `deletion_fallout` gets the conditions as well as the blocks). A running block holds a copy of its rule (`Block::condition`) and of its lock condition (`RunLock::Condition`). **A new kind of condition** is a variant of `Rule` with what it means in `active` / `next_change`, an editor in `conditionForm`, and an option in the CLI's `condition new|edit`.
- `src-tauri/src/webhook.rs` – a **webhook condition** (`Rule::Webhook(Hook)`, `type: "webhook"`): one URL (GET parameters allowed, no headers or tokens), `method` get / post, `interval` seconds (at least 60), two matchers (`when_true`, `when_false`: `on` status / body / both, `status`, `body` that must equal the response body, white space aside) and a `fallback` (active or not). `Hook::judge` tries the true matcher, then the false one, else `Outcome::Neither` (the fallback). **`Rule::active` never waits for the network**: `webhook::answer` reads what a poller thread (started by the first question, polling each entry once per interval, dropping entries nobody asked about for 10 minutes) last found, and uses the fallback when there is none yet or it is older than three intervals; a failed request leaves the last answer to age. `ureq` makes the request (10 s timeout, five redirects, TLS checked, body cut at 64 KiB). It has no `next_change` (like a drive: tiles say "active since … is true"), `tightened_by` allows only the same hook (so a locked block's webhook condition cannot change), and a combination with a webhook has no time either. `webhook::test` is the editor's Test button (`test_webhook`, local to the app) and `bullseye-cli condition test`; the window's interval is in minutes, the CLI's a duration (`--every 5m`). The matchers are set in the editor by a dropdown (HTTP code only, body only, both)
- `src-tauri/src/schedule.rs` – `Week`: per weekday (Monday first) spans in minutes `[start, end)`; text form `Mon-Fri 08:00-17:00; Sat 10-12` (`parse` for the CLI, `describe` for the window and the CLI)
- `src-tauri/src/localtime.rs` – local weekday/time for weekly schedules, in the time zone Windows had when the block started (kept in `state.json` as `zone`, since standard users may change the time zone); daylight saving followed
- `src-tauri/src/lock.rs` – lock methods: `none` (stop any time), `duration` (cannot be stopped, ends the block when up), `until` (the same, ending at a local date and time, `2026-10-06 18:00`, read in Windows' time zone when the block starts: `datetime.rs`, `localtime::Zone::instant`), `delay` (`Lock::Delay`, `RunLock::Delay { delay, asked }`: stopping is asked for with `AskToStop`, counts down on internet time, `AbortStop` ends the wait, and once it is over `Stop` works; the status carries `stop_delay` / `stop_remaining` in numbers and words; at most 24 hours), `until_restart` (cannot be stopped, ends when Windows restarts: `boot.rs`; a shut down with Fast Startup is not a restart), `condition` (cannot be stopped while its chosen condition, by id, is active: a schedule at its times, a flash drive while it is not connected, `condition.rs`) `text` (stopped only by typing its text in exactly: the window shows it above an input that refuses paste and drop, the client sends `text` with the stop, and the service compares it, line breaks aside; the CLI refuses to stop one, as a terminal cannot refuse a paste) and `password` (stopped only with its password; the client sends `password`, the service keeps `hash`)
- `src-tauri/src/drives.rs` – flash drives and other USB disks, told apart by the serial number their hardware reports (Storage Management's `MSFT_PhysicalDisk` on the USB bus, which also covers UASP disks), never by content or drive letter: `connected()` (what the lock's settings scan, `connected_drives`, and `bullseye-cli drives`) and `is_present(serial)` (what a flash drive condition asks, whenever the service decides whether a block is active or can be stopped, looked up at most every 2 s; if Windows cannot be asked, the drive is away and the lock holds). A drive with no serial number is not offered, and drives of a batch that share one look like one drive
- `src-tauri/src/datetime.rs` – a local date and time (`2026-10-06 18:00`, written out `Tuesday 6 October 2026, 18:00`), platform-free; `localtime::until` is what the window's `describe_until` and the CLI show of an until lock (refused once it has passed)
- `src-tauri/src/boot.rs` – which start of Windows this is: a random id in a volatile registry key (`HKLM\SOFTWARE\bullseye-boot`, HKCU for the debug build's embedded service), gone after a restart; a block locked until restart is not resumed under another id
- `src-tauri/src/duration.rs` – durations: `5s`, `10m`, `3h`, `1d`, combined (`2h 5m`, `1d12h`) or in words; `countdown()` writes them out, short
- `src-tauri/src/clock.rs` – internet time (SNTP) that timed blocks are measured against, so moving the Windows clock does nothing
- `src-tauri/src/unlock.rs` – **the escape hatch**, unlocking (`UnlockDelay`): a countdown, no password. The user sets how long it takes, 0 to 24 hours (default 0: **an unconfigured app can always unlock**); with a delay, unlocking is asked for (`AskForUnlock`), counts down on internet time, can be aborted (`AbortUnlock`) at any time, and once the countdown is over `Unlock` ends every block (and uses the request up) or it is aborted. A longer delay is free to set; a shorter one needs unlocking to be ready (`remaining` is `Some(0)`), or it would be a way around the wait. Kept in `unlock.json` in the service's data folder; whatever is wrong with that file (gone, unreadable, nonsense) means no delay: a fault opens the hatch, never closes it, and failing to write it never stops a request. **Its tests are many on purpose** (here and in `handler.rs`: every lock method, the countdown, abort, shortening, restart, bad files, the clock moving): keep them passing, as this is the way out. Also the hashing of password locks (`new_hash`, `check_hash`: a random salt each). **The other way to unlock** (`Way`, kept in `unlock.json` as `way`): the delay is always there as the fallback, and besides it there can be one other way, chosen like a block's lock but never the delay (`Request::SetUnlockWay { way: Option<Lock> }`, `handler::set_unlock_way`): only a condition, a custom text or a password: a condition is **locked while it is active**, as a block's lock is, and open when it is not (`Opening::While`: a copy of its rule and the time zone, as a running block holds them), a text typed in or a password (only its hash is kept; `Way::answered`). Unlocking is ready when the countdown is over **or** the way lets go (`Way::is_open`, or an answer given with `Request::UnlockWith`): either, never both (`handler::unlock_with`); what a condition cannot say counts as locked (`Rule::active` errs towards blocking), and the delay is still the way out. Setting one makes unlocking easier, so it needs unlocking to be ready or no block to be locked (`UnlockDelay::set_way`, like a shorter delay); removing it is free. The status carries `way` (a password without its hash), `way_open` and `way_left` / `way_left_words`; Settings has the dropdown (`main.js`: the lock methods' own labels and forms from `LOCKS`) and, for a text or password way, an "Unlock with text / password" button; the CLI has `unlock --password` and `unlock-way`
- `src-tauri/src/filters.rs` – site lists: plain address prefixes plus `*` (user rejected full uBlock syntax as too complex); **a domain also covers its subdomains** (`tweakers.net` is `gathering.tweakers.net` too, one entry per site; an entry with a `*` in its domain goes by what it says, so `*.tweakers.net` is only the subdomains), and exceptions are entries in the allowed list. Used for the block list and the always-allowed list, which **wins**. Only web pages are matched, never the browser's own pages, so a lone `*` blocks every site and leaves the browser usable
- `src-tauri/src/lists.rs` – `Entries` (a block list's lists as typed; what is saved, sent and shown carries them, flattened into its own fields) and `Lists` (the same, read and checked; `parse`, `entries`, `has`): the one place a new list is made. `patterns.rs` – a list of `*` patterns matched against a whole text, ignoring case (window titles, and Store app names given exactly; a lone `*` title matches every window, which the user chose: refusing it only let `*e*` through instead, and what must never close is spared where windows are closed: Bullseye's own and Windows' shell, `tab_closer::close_windows_by_title`, and Windows' Store apps, `store_apps::PROTECTED`. The program list is different: it refuses any entry that would match a protected program, `*` included, as closing those breaks Windows). `store_apps.rs` – Store apps by exact package family name (`Microsoft.WindowsCalculator_8wekyb3d8bbwe`; no `*`, `lists::store_apps`, as the window ticks them and the CLI takes them alike): which app a program belongs to from where its exe is, the installed ones for the editor to tick (`installed_apps`, PowerShell's `Get-StartApps`, protected Windows apps left out; it also takes the list's own entries and returns those not installed here, as after an import from another computer, named from their family name: `offered`, `readable`, shown as "Claude (not found on this PC)") and the `PROTECTED` families that are never closed
- `src-tauri/src/programs.rs` – programs to close: exe names with `*`, `.exe` added when missing, and a protected list (Windows' own, this app and its CLI, WebView2) that is never closed and refuses entries that would match it
- `src-tauri/src/tab_closer.rs` – the worker in the app doing the closing, every second and sooner on events (`wake.rs`; a pass that wants another soon, `QUICK`, waits 150 ms). A Chromium window is looked at in full once (`Closer::layout`): all its tabs are listed, the parent of the first is the tab strip, kept, and tabs are found only inside it; a window is an **app window** (closed whole) only after no tabs were seen on two passes and for a second (`judge`; a failure to look counts for nothing, it used to close whole windows), and a window that had tabs never becomes one. **And only a browser's own window can be one** (`is_browser`: the file name of its program is in `BROWSERS`, else `Layout::NotABrowser`, left alone): Spotify's desktop app is a Chromium window with an address bar of its own (`OmniboxViewViews`, `MultiContentsView`) and no tab strip, and was closed as an app window of spotify.com; the same goes for any app built that way. A window whose program cannot be told is left alone too. A blocked page read from the address bar alone (documents not exposed yet) is closed only when seen again 80 ms later with the same tab selected, and that tab is closed by its UI Automation id (`Pending`, `agrees`). **The address bar is also a second witness while a page is exposed** (`tick`: it counts only when it names another site than the exposed page, `host_of`, as an exposed page of the same site is trusted, the bar may show less of it): a heavy page such as nrc.nl exposes its accessibility tree late, and the browser shows where a tab is going long before, so the bar closes it through the same pending path. `close_blocked_tab` re-checks a bar page against the bar. Each close says in `app.log` whether it came "from the address bar" or "from the page" and how long after the page was first seen (`first_seen`). Steps over 50 ms are written to `app.log` (`slow:`). Firefox reads where a page is only when some page is blocked. Enforcers (`state::Enforcers`, checkboxes in the UI for the sites and Obsidian, fixed while a block runs): with the site list, Chromium tabs, split view and app windows (`chrome --app=<url>`: no tab strip, closed whole) and Firefox tabs and split view (Firefox exposes every tab's page, matched to its tab by title, and a split view's two tabs by their names ending alike but for the last word, in any language); with the program list, programs (asked to close, ended after 3 s); with the Store app list, the programs running from a package's folder under `WindowsApps` (`store_apps::family_of`), the same way; with the window title list (less its always-allowed titles, `allowed_titles`, which win as the always-allowed sites do: `Lists::blocks_title`; with a budget, like the sites, `Lists::exceptions`), windows by their title, the window only, never its program: closed (asked to, again every 3 s) or **minimized** instead (`window_titles_minimize`, a radio group of Close / Minimize in the editor, `choiceOf`). **The program, Store app and title lists have no switch** (the user chose this): a list with entries acts, an empty one does nothing (`Enforcers::all` has them always on; switches of older files, `exe_names`, `store_apps`, `window_titles`, are ignored). Which is `Active::title_action`: closing wins across blocks; a minimized window is not touched again and does not count as in use for a budget, an open one does for closing; dialogs (owned windows) and tool windows are not minimized; a window still up 1 s after being asked (`MINIMIZE_AFTER`) cannot be minimized and is left alone, never closed instead, noted once. A locked block's list may go from minimizing to closing, not back (`Enforcers::turned_off_by`). While a block minimizes, any window coming up wakes the worker (`wake::watch_every_window`, also `EVENT_SYSTEM_MINIMIZEEND`), so a window brought back from the taskbar goes down again at once; without a list, Obsidian's web viewer
- `src-tauri/src/wake.rs` – what makes the worker look again at once instead of at its next second: in the app a WinEvent hook (out of context, its own thread with a message loop) on a top-level Chromium or Firefox window's title or value changing or coming to the foreground (a page's own events come from its child window and do not count); from the service, WMI's process start trace (needs SYSTEM) for a program a running block would close (or Obsidian with its enforcer on), passed on through the named event `Global\bullseye-wake` (only SYSTEM can create or set it; interactive users may wait on it). The worker waits on both with its 1 s timeout, at least 100 ms between passes. The 1 s pass stays, and so does the app's policy request each second, which is how the service knows it is alive. `app.log` says what each close came from (`Woken`): "on a window event", "on a program starting" or "on the pass every second"
- `src-tauri/src/state.rs` – the running blocks on disk (`%ProgramData%\bullseye\state.json`, SYSTEM-owned; each with its `parts`, condition, zone and locks; only today's format) and the `Enforcers` table (one place to add an enforcer)
- `src-tauri/src/watchdog.rs` – the service's watch over the app (`AppSlot`) and the log writer
- `src-tauri/src/sync.rs` – `locked()` (locks that survive a crash) and `spawn_critical` (a crash in a long-lived thread ends the process, so Windows restarts it)
- `src-tauri/src/setup.rs` + `src-tauri/windows/hooks.nsh` – `--install` / `--uninstall`, run by the NSIS installer (no update path: uninstall first)

**Naming.** The product is **Bullseye** (it was "Site Blocker"). Everything a process or the system goes by is lowercase `bullseye`: the exe (`bullseye.exe`, `mainBinaryName`), the service's key name, the pipe, the data folders (`%ProgramData%\bullseye`, `%LOCALAPPDATA%\bullseye`, `bullseye-dev`), the identifier, safe-mode keys, file and artifact names. Text a person reads is capitalised "Bullseye": the window title and header, messages and errors, the installer's dialogs, `productName` (so `C:\Program Files\Bullseye` and Settings > Apps) and the service's display name. Development environment variables stay uppercase by convention (`BULLSEYE_SHOW`). So is the Cargo package, and with it the dev build's exe.

## How the pieces keep each other alive

The `bullseye` service runs as SYSTEM, starts at boot, and holds the block definitions, the running blocks, internet time and the unlock hash. The tray app (user session) asks it every second what to enforce, does the closing, and keeps no state; it keeps enforcing the last answer if the service is briefly unreachable.

- The service does not accept a stop request, and its access list (`registration.rs`) gives only SYSTEM stop / change / delete. If it fails by itself, Windows restarts it at once (failure actions).
- The service starts the app at every logon and, **while any block runs** (also outside its condition), starts it again within ~1 s of it ending. Which process is "the app" is the service's decision: the one it launched, or the installed exe in the console session that registered; never a matter of the process name. An app that has not asked for its policy for 5 s (20 s after starting) during a block is ended and started again, which covers a suspended app. After a sleep the app gets a fresh start instead.
- If the service is not running, the app asks Windows to start it (interactive users may *start* it, nothing more).
- Reboot mid-block: the service reads `state.json` back and resumes every running block with its time left.

**"Unlock"** in the UI (`unlock_all`, with `request_unlock`, `abort_unlock` and `set_unlock_delay`) is decided by the service (`unlock.rs`, `Overview::unlock` says where it stands: the delay, and the time left or not asked for). On the Settings page: with no delay it is one click (after a confirmation); with one, Request unlock, a countdown with Abort, then Unlock and Abort when it is over. It ends **every** running block (the definitions stay); the app stays open, with nothing to enforce. It is the only way to end a locked block early. `bullseye-cli unlock` does the same (`unlock-delay` sets the delay). (Unlock used to quit the app too; the user preferred it to stay.)

### Deliberately not hidden

Per the user's decision: nothing here is obscured. The service is called "Bullseye" in the services list (its key name is `bullseye`), the app runs under its own name in Task Manager, it is listed under Settings > Apps, and `%ProgramData%\bullseye\service.log` (administrators can read it) and `%LOCALAPPDATA%\bullseye\app.log` say what happened. The mechanism is friction, not secrecy.

**The honest ceiling** (do not claim otherwise in the UI): an administrator who knows how can run a shell as SYSTEM (for example PsExec `-s`), take ownership of the service object or its data folder and rewrite them, delete the service from the Windows recovery environment, or edit the registry offline. The app is a process of the user it protects against, so someone who can inject code into it can keep it asking for its policy while it enforces nothing. Lock deadlines and schedules are in NTP time; offline, time only advances while the service runs (from `seen` in `state.json`). A running block's time zone is pinned when it starts; an administrator can still rewrite Windows' time zone rules in the registry. Spoofing NTP needs admin. The password hash is in the binary, so a short password can be brute-forced offline. What changed from the old per-user design is the effort: "End task" no longer works.

### Install / remove

`npm run build` makes a **per-machine** NSIS installer (`src-tauri\target\release\bundle\nsis\`), which needs admin and installs to `C:\Program Files\Bullseye` (never a user-writable folder: the exe runs as SYSTEM). Tauri bundles every binary of the package, so `bullseye-cli.exe` lands next to `bullseye.exe` (not on `PATH`). The hooks (`windows/hooks.nsh`) run the app with `--install` (create the service, lock it down, safe-mode keys, start it) and `--uninstall` (the service removes itself, its data and the app). Uninstall is **refused while any block is locked right now** (a duration or until lock, until restart, a lock schedule while it is active, or a password; exit code 2, internet time). If a service is registered but does not answer, the uninstall also stops (exit code 1, nothing removed); with no service registered it carries on. The installer cannot stop the service itself, so it asks over the pipe. `.github/workflows/build.yml` builds the installer as an artifact for every push.

### Recovery: when your own test locks you out

The installed service cannot be stopped by you, by design, and a locked block refuses uninstalling. So test installs in a Windows virtual machine with a snapshot; on a real machine use short blocks (`5s`) and know that unlocking is there (an unlock delay, if you set one, makes it a countdown). If it still goes wrong, as an administrator, open a shell as SYSTEM (Sysinternals `psexec -s -i cmd`) and run:

```bat
sc delete bullseye
taskkill /f /im bullseye.exe
reg delete "HKLM\SYSTEM\CurrentControlSet\Control\SafeBoot\Minimal\bullseye" /f
reg delete "HKLM\SYSTEM\CurrentControlSet\Control\SafeBoot\Network\bullseye" /f
rmdir /s /q "%ProgramData%\bullseye"
```

`sc delete` comes first: it marks the service for deletion, so Windows does not start it again when `taskkill` ends the process. Without PsExec, Task Scheduler gives a SYSTEM shell: save those lines as `C:\recover.cmd`, then `schtasks /create /tn recover /sc once /st 00:00 /ru SYSTEM /tr C:\recover.cmd /f`, `schtasks /run /tn recover`, and `schtasks /delete /tn recover /f`. Last resort: the Windows recovery environment's command prompt runs as SYSTEM too.

## Dev workflow

- `npm run dev` needs no service: in a debug build the app runs the service's logic inside itself (`service::embedded`), with its files in `%LOCALAPPDATA%\bullseye-dev`. Kill it at will. `BULLSEYE_USE_SERVICE=1` talks to a real installed service instead. Release builds contain none of this (`debug_assertions`); `cargo check --release` must stay warning-free. The CLI always needs the real service (`cargo run --bin bullseye-cli -- status`).
- There is **no window until you click the tray icon**. Debug aids: `BULLSEYE_SHOW=1` (open at start), `BULLSEYE_REOPEN_AFTER_SECS=n`, `BULLSEYE_UI_TIMEOUT_SECS=n` (shorter keep time).
- Run `npm run dev` as a background task; it rebuilds and relaunches on changes in `src-tauri/`. Changes in `src/` are not picked up automatically – `touch src-tauri/src/main.rs` to force a relaunch.
- Dev log lines contain ANSI colour codes (`Running\e[0m \`target\...`), so patterns like `'Running \`'` never match. Wait for a relaunch by matching `bullseye.exe`, and check the real log text before writing any wait loop.
- Look at UI changes in a browser without Windows: the page's modules do not load from `file://`, so serve `src/` (`python3 -m http.server` in it) and open `index.html` in Playwright's Chromium with a stand-in `window.__TAURI__` (an `addInitScript` that answers the commands from memory); check narrow (440 px) and wide, light and dark.
- Edit JS/HTML containing escapes (`\n`, regexes) with the Write/Edit tools, not heredocs or Python string replacement – escapes got mangled into literal newlines several times. Syntax-check the page script with `node --check` after edits.
- From Linux (the cloud sessions): `rustup target add x86_64-pc-windows-msvc`, then `scripts/linux-tests/clippy-windows.sh` lints everything as CI does (no linking; it gives ring's bit of C clang-cl and stub headers), and `scripts/linux-tests` runs the tests of every platform-free module, the CLI's included (see "Test coverage").
- `cargo test` (in `src-tauri/`) runs some 200 tests. Ignored on purpose: the network clock, `the_pipe_answers_like_the_app_expects` (`-- --ignored the_pipe`; no service may be installed, it takes the pipe name) and `a_real_browser_tab_is_closed` (needs a Chromium browser window open on example.com). Also run `cargo clippy --all-targets` (clean), `cargo check --release` and `cargo fmt` (`src-tauri/rustfmt.toml`). CI runs `cargo fmt --check`, then `cargo clippy --all-targets -- -D warnings`, then `cargo test`, then builds the installer.

## Test coverage

**Always pursue full test coverage.** Every change comes with tests for what it does, and every line of logic is covered: each branch of a rule, each error a function can return, each message a person reads (`Block::locked`'s wording, the CLI's output). A finding, a fix or a question that turned out to matter (such as what a per-item budget does to Obsidian's enforcer) gets a test that pins the answer. Look at the coverage before finishing, and cover what a change left uncovered, also in code it did not touch.
- **Measure it**: `cargo llvm-cov --manifest-path scripts/linux-tests/Cargo.toml --summary-only -- --skip only_the_installed_app --skip the_app_of_a_program` (on Windows, `cargo llvm-cov --summary-only` in `src-tauri/`; `cargo install cargo-llvm-cov` and `rustup component add llvm-tools-preview` first), or `--text` for the lines missed. `scripts/linux-tests` builds the platform-free modules straight from `src-tauri/src` (`#[path]`, never a copy) with stand-ins for `boot`, `drives`, `watchdog`, `client` and `windows-sys`; a module that becomes platform-free goes into its `lib.rs`, and one that cannot build there keeps its Windows calls behind a function the tests do not need (as `store_apps::installed` does with `#[cfg(windows)]`).
- **What cannot be covered** in a unit test is kept thin and away from the logic: Win32 and UI Automation calls (`tab_closer`, `wake`, `watchdog`, `pipe`, `registration`, `service`, `boot`, `drives`, `localtime`'s Windows zones), the Tauri window (`lib.rs`, `ui.rs`), the network (`clock`'s SNTP; a webhook's requests are tested against a server on 127.0.0.1) and the page's JavaScript (checked in a browser, see "Dev workflow"). What such code decides is pulled out into functions that are tested.
- A test runs everywhere CI runs it: no internet, no real service, no files outside the temporary folder; a time is set with the block's clock (`Clock::at_least`), never waited for longer than a second or two.

## Adding an enforcer, a list, a condition kind or a lock method

The UI is built from tables so these need no new markup:
- **Enforcer**: a field in `state::Enforcers` and a line in `Enforcers::all`; an entry in the right `SECTIONS` group in `src/js/forms.js` (`key` = the field name). If it acts per block, a method on `block::Active` that combines the running blocks (see `blocks_page` / `blocks_program`).
- **List** (inside a block list): every layer shares `lists::Entries` (the lists as typed, flattened into `definitions::BlockList`, `state::SavedPart`, `block::RunningList` and `proto::Policy`) and `lists::Lists` (read and checked, held by `block::Enforced`), so a list is a field of both, a line in `Lists::parse`, `entries` and `has`, an arm in `Entries::field`, a `Uses` variant for its enforcer and a method on `block::Active`; an entry in `LISTS` and its key in a `SECTIONS` group; a line in `cli::LIST_OPTIONS`. Entries missing from a saved file read as empty.
- **Condition kind** (other than a weekly schedule, a flash drive or a combination): see `condition.rs`; the CLI's `condition new|edit` takes an option for it. A kind that is not a leaf needs a rule for `Via` / `tightened_by` as the combination has.
- **Lock method**: a variant of `lock::Lock` (tagged by `method`), what it starts as (`block::StartLock`, from `handler::start`) and runs as (`block::RunLock`, and what it means in `Block::locked`); an entry in `LOCKS` with its `form` (the modal's fields and how to read them, if it has settings), `describe` and `confirm` (what starting asks, or null); an option in `cli::parse_lock`.
- **Anything the window can do**: also in the CLI (see `cli.rs`).

## Design system (Carbon)

All UI uses IBM's **Carbon design system** (https://github.com/carbon-design-system/carbon), through `@carbon/web-components` (`cds-*` elements), `@carbon/styles` and IBM Plex:
- **Follow Carbon's paradigms; don't work around them.** When a request can be met the Carbon way, do it that way, even if a hack would match the request more literally; when it cannot, say so and propose the Carbon-native alternative instead of overriding a component. Never restyle a component's shadow DOM (adopted style sheets, `!important` against its internals); use only its attributes, slots, `::part`s and the theme tokens.
- **Only Carbon components.** Use a `cds-*` component for every control, message and container (buttons, inputs, textareas, checkboxes, selects, tiles, tags, notifications, modals, overflow menus, breadcrumbs, tabs, tooltips). No hand-made controls and no other UI library. A component not yet in the bundle is added to `scripts/carbon/entry.js` (import the specific file, e.g. `.../tag/tag.js`, not the folder's `index.js`) and `npm run vendor` is run; the same goes for icons (`@carbon/icons`, used through `carbonIcon(name, slot)`).
- **Only Carbon tokens.** Colours are `var(--cds-*)` theme tokens, spacing is `var(--cds-spacing-01…13)`, type is Carbon's `cds--type-*` classes in IBM Plex. No hex colours, pixel spacing or other fonts in the page's CSS; `app.css` is layout only.
- **Themes**: `g10` in light mode and `g100` in dark mode, following Windows (the script at the top of `index.html` switches the `cds--g10` / `cds--g100` class on `<html>`). Check both. Tiles and fields are white on the grey g10 page; do not put the content on a layer of its own (a panel on `--cds-layer-01` made them white on white, and `cds--layer-two` is not in the vendored CSS).
- **Responsive**: layout with Carbon's CSS grid (`cds--css-grid`, columns with `cds--css-grid-column cds--sm:col-span-4 cds--md:… cds--lg:…`, and its breakpoints (sm 320, md 672, lg 1056, xlg 1312, max 1584). Put cards straight into the page's grid as columns, so their edges line up with the page header; a nested `cds--subgrid` hangs into the gutters and does not. The block tiles are one per row, full width (`sm:4 md:8 lg:16`), like the empty-state tile, so they resize smoothly with the window; from md up a tile's Start/Stop sits at the right of its row, level with the last summary line (no text under the button). (Carbon allows tiles at any span; its own component for a list of items with status and actions would be a data table, which was not chosen.) The window is resizable down to 440 × 480; every view must work from there up (440 px is as narrow as an editor's Delete, Cancel and Save fit on one row, 436 px measured with a 15 px scrollbar, Windows' is 17: the user found them wrapping ugly; change it with them), with no horizontal scrolling. Carbon's `col-span` classes set `display: block`, so a column that is also a flex box needs that restated (see `.block-tile`).
- **Fixed and scrolling sections**: no header bar (the window title names the app). The window is a flex column: the fixed section, `.pinned` (white, the whole width: `--cds-layer-01`; the tabs sit in a full-width `.tabbar` with a subtle line above and below, and no padding under it), holds from the top the view's heading (`#head-list` / `#head-editor` / `#head-settings`, one shown by `showView`: the breadcrumb of an editor, the large title, the description line, and a list page's New button), then the pages' `cds-tabs`. What scrolls is `#scroller` (it alone: `body` does not), holding `main` under the tabs, on the grey page background (with the padding that used to be under the tabs at its top), in the same 66rem grid as the tabs so both are exactly as wide. Messages (`notify`) are **not** pinned: they sit at the top of the scrolling part, in their view, and an error scrolls into view (`notify`'s `scrollIntoView`).
- **Tabs**: Carbon's default (line) tabs, not the contained style (tried twice and rejected by the user; if it ever comes back, `type="contained"` must be on every `cds-tab` as well as the `cds-tabs`, or they stay line tabs). Carbon's source: https://github.com/carbon-design-system/carbon (the tabs are in `packages/web-components/src/components/tabs`).
- **Navigation**: Carbon's header global actions are for tools and panels, not pages, so the pages are `cds-tabs` in the fixed section, under the heading (so they line up with the content). One `cds-tab` per top-level page, an icon before its label (`locked` blocks, `list-checked-16` block lists, `rule-16` conditions, `settings`; slotted with the label, as Carbon's tabs with icons). Below md (672 px) they are Carbon's icon-only tabs (`main.js` sets `icon-only` on each tab and `icon-size="default"` on the tabs, which lets their tooltips out of the tab bar): square, named by a tooltip and their `aria-label`, so the four fit at 360 px. The router sets the tabs' `value` (`markPage`); an editor, and a block list or condition made from a block, count as their page's tab. No header links or global actions (those are for tools and panels, not pages), no hamburger, no side nav (folds into a hamburger below 1056 px). A page below a top-level one (the editor) has a `cds-breadcrumb` above its title, built by `setCrumbs`: the page as a link, then the current page (`is-currentpage`), e.g. "Blocks / Work hours"; made from a block it is one deeper, "Blocks / Evening / New block list". Below 672 px Carbon would stack the breadcrumb items, one per line; `app.css` makes the items inline (`.trail cds-breadcrumb-item`, the hosts' own display), so the trail stays on one line as it does from md up and wraps only when it is longer than the window.
- **Layout**: every view is one full-width column (`sm:4 md:8 lg:16`) in `main`, which is capped at 66rem (Carbon's lg) and centred beyond it. So the content fills the window with Carbon's grid margins until it is 66rem wide, then stays that wide and centred, and every view is exactly as wide as the others. Never give one view's content a narrower width or a `col-start` offset: it makes the views differ and the margins jump at breakpoints.
- **Breadcrumb**: `#trail` is always shown, the topmost thing of the fixed section: the editor's trail (`openEditor`), and elsewhere just the page itself, as in Carbon's own single-item example: a link with a trailing slash ("Blocks /", "Settings /"; `showView`; the editor's trail has no trailing slash), so the heading is at the same height on every tab and the editor.
- **Names**: a new item has a name already, the first free "Block 3" / "Block list 1" / "Condition 2" (`freeName` in `kinds.js`, texts `<kind>.autoName`), in the name text box of its editor (a title with an edit icon on hover was tried and dropped as more confusing than nice). **A name can always be changed**, also on something a locked block holds: the other fields of such an editor stay disabled, Save stays enabled, and the service accepts a locked block's save when only its name differs (`handler::edit_block`; a block list's or condition's own save is already "stricter or equal"), the running block following (`refresh_running`).
- **Tagline**: under the title row (the New button is on that row), across the whole width and with room above it (`.tagline`), so a long one wraps under the button, not beside the title.
- **New button**: in the fixed heading, level with the title (the heading's row does not wrap). Its label is always just "New" (`common.new`) with a + icon, at any width, so it fits on the row; the page's own name ("New block") is its aria-label. (A below-md icon-only `cds-icon-button` with a tooltip was tried and dropped. If one comes back: the icon goes in the `icon` slot, or Carbon does not make it icon-only and it is as wide as its tooltip.)
- **No sideways shift** between pages with and without a scrollbar: `#scroller { scrollbar-gutter: stable }` keeps the scrollbar's width reserved without drawing a scrollbar. The strip is on the grey page beside the content, so it does not show (on `html` it cut the white fixed section short of the window's edge, which the user found ugly). The fixed section's grids keep the same room at their right (`.lane`, `--gutter`, measured by `main.js`), so they line up with the content, while its white and lines go to the edge.
- **Every button has an icon** (`icon` slot, `carbonIcon`): Carbon keeps 63 px at the right of every `md`/`sm` button for one, so an icon-less button shows it as empty space, and overriding that with `::part(button)` would be working around the component. The dialog's footer buttons (Cancel and the confirm button) have none, by the user's choice. Icons used are in `scripts/carbon/entry.js`. A new button on a page gets one.
- **No borderless (ghost) buttons** (the user finds them inconsistent next to the outlined and filled ones), **except** the small Edit icon button beside each block list in the block editor, which the user wants as it was (`ghost`, `sm`, not the `tertiary` `md` it was changed to). Elsewhere: (the user finds them inconsistent next to the outlined and filled ones): use `tertiary` for a minor action, `danger-tertiary` for a destructive one, also for icon buttons and small ones in tiles and forms.
- **Buttons**: `size="md"` (40 px, the height of a text field) for every button and icon button, tiles included, and for the dropdown beside a tile's Start (never `sm`: two heights next to each other looked wrong); not Carbon's default `lg`, which is too big for this app. The editor's Delete is `danger-tertiary` (red outline). The web components' kinds have one dash (`danger-ghost`, `danger-tertiary`), unlike Carbon's CSS classes (`cds--btn--danger--ghost`); an unknown kind silently falls back to the default look.
- **Making things on the way**: the block editor has a New block list and a New condition button (tertiary), and an Edit icon button (`cds-icon-button`, tertiary, tooltip) beside each block list and an Edit condition button for the chosen condition, which use the same detour (`#/edit/<id>/lists/edit/<list id>`; no Delete there, nothing to tick afterwards). The New ones keep the block as edited so far (`detour`: where to go back, the draft, what to do with the new item), open that kind's editor one level deeper (`#/new/lists/new`, `#/edit/<id>/conditions/new`), and on Save go back to the block with the new item ticked or chosen; Cancel goes back unchanged. Choosing the Condition lock with no condition yet asks whether to make one (`#/lock/<id>/conditions/new`), and the lock is set to it once saved; no, and the lock stays as it was. Not a modal: a block list or week grid is a whole page, more than Carbon's modals are for (short tasks).
- **Block list editor**: after the name, its sections (`SECTIONS`: websites, programs, other) are a `cds-accordion` of `cds-accordion-item`s that open and close; the sections with content are open when the editor opens (`listForm`'s `fill`): one with a list when any of its lists has an entry, the one with only an enforcer ("other") when one of its enforcers is ticked, so also in a new block list (which has Obsidian's on; its websites are open too, to start typing in); the rest are closed. Spell checking is off for the whole page (`spellcheck="false"` on `<html>`, inherited by every field, also inside the web components): names, domains and exe names are not words.
- **Patterns**: page title `cds--type-productive-heading-05` with a short description; sections `productive-heading-03`, each with a line on what it is for (`section` in `forms.js`), as the Settings page has them: every part of the block and condition editors below the name has its heading (a condition's week, drive or combination too), spaced apart (`--cds-spacing-09`) with **no divider lines**, the only line being the one above Delete / Cancel / Save (the user asked for this; the block list editor keeps its accordion); errors and states as `cds-inline-notification` (low contrast) at the top of the view; anything that cannot be taken back asks first in the one `cds-modal` (`ask()` in the script, focus on Cancel via `data-modal-primary-focus`): deleting (`danger`), and starting a block that cannot be stopped (`LOCKS[method].confirm`; a new lock method must say whether it asks). The same modal holds short forms (`ask({fields, read})`, which stays open while `read` gives null and marks the fields with `invalid()`): a lock's settings and the password that stops a password-locked block. The tile itself has only the lock's method select next to Start; choosing a method with settings (`LOCKS[method].form`) opens its form, and Cancel keeps the old lock. The method is a `cds-dropdown` (not a `cds-select`, the browser's own control, which says nothing when the choice already made is chosen again): choosing another method asks for its settings, and clicking the item of the current one opens its settings again (`addBlockControls`); the ⋮ menu's "Lock settings" does too. Each tile's ⋮ menu has Edit, Duplicate (the service makes and names the copy; a notice names it) and Delete; a block's also "Lock settings", where the current lock's settings are changed (hidden for a lock without settings; menu items have no "…"). Each form starts from the block's settings for that method, its lock's or the kept ones (`settingsOf`). The until lock's form is Carbon's date picker (`date-format="Y-m-d"`, so its value and text are ISO) and time picker side by side (`.date-time`). A block tile's summary lines have a 16 px icon in front (`list-checked-16` block lists, `rule-16` the condition (the Conditions tab's icon, whatever its kind, "always" too), `locked` / `unlocked` lock): `summaryOf` gives `[icon, text]` lines. A password already set is never known to the window (only its hash is kept), so its fields hold 8 dots (`KEPT`) as a real value of normal colour, not a placeholder, so placeholders keep their own style. Clicking or tabbing into either field clears both; leaving both empty puts the dots back; saving them unchanged keeps the password. The form is not focused on opening, which would clear them. A tile shows a plain `locked` icon (not a button) where its options menu would be while it cannot be changed: a block that is locked (a running one that is not has its menu, without Lock settings). A block list or condition a locked block uses keeps its menu (its editor takes only stricter changes) and gets an "In use by a locked block" tag; its Delete is disabled while a locked block uses it (deleting a running block, or what one uses, otherwise goes ahead and says so in its question). A running block's condition line says whether it enforces now, as a lock's line says its state (`runningRuleLine`: `Active during …` / `Inactive outside …` for a schedule, a drive `Active since … is unplugged` / `Inactive since … is plugged in`, a combination with a drive `Active since … is true` / `Inactive since … is false`; a condition lock the same with Locked / Unlocked), with the time to the change when the condition has one (never with a drive in it); there is no line of its own for it, as the tag says it too. Wording by kind comes from `wordingOf` (during / drive / true), the same for a block's condition and a lock's, and a condition lock is one line (`conditionLockText`) whose icon follows its state.
- **The week grid** (`weekEditor`, `.week` in the page's CSS) is the one hand-made control: Carbon has no calendar or time-grid component and the user asked for a weekly calendar view. It is plain layout coloured with Carbon tokens only and `aria-hidden`. Its hour labels are centred on the lines they name, 00:00 on the top edge to 24:00 on the bottom one (each spans the two half-hour rows above its line and the two below). The user removed the Times text field above it as confusing, so the grid is the window's only way to set a weekly schedule; the CLI's `condition new|edit --times` is the typed one. If Carbon ever ships a suitable component, use it instead. The one exception to "never touch a component's shadow DOM": text areas side by side (sites to block, always allowed) keep one height when one is resized with its handle (`sameHeight`). `cds-textarea` has no attribute or part for its height, so the same inline height the browser's resize handle set on the dragged one's inner `<textarea>` is set on the others in its row; nothing else is touched. Stacked (narrow window), each keeps its own. The modal's full-width footer buttons are Carbon's design; keep them, with short fixed labels ("Start locked", "Delete"): they have one height, so a label with a time in it runs out of the button. The time goes in the heading and body.
- Web-component quirks: a `cds-dropdown` (used for every choice from a list, never `cds-select`) takes `title-text`, `helper-text`, `invalid` and a `label` as its placeholder, and always `autoalign` (without it the open list is part of the page and makes the page scroll when the dropdown is near the bottom, which a native select never does; with it the list flips upwards where there is no room); its events are `cds-dropdown-selected`, and its value only matches items present when it is set; icons go in the `icon` slot (`cds-button`, `cds-overflow-menu`); an overflow menu's icon needs the class `cds--overflow-menu__icon` (without it the icon takes the button's white and vanishes on a light tile); an open `cds-overflow-menu` moves its body out of the host, so listen on the items; read values from the elements (`.value`, `.checked`), whose events are `input` and `cds-checkbox-changed` / `cds-select-selected`. `cds-textarea` sets its helper text's `max-width` from its own measured width, through a ResizeObserver that it disconnects when taken out of the page and makes again only on its next update: a text area moved out of the page and back (a reused form) keeps a 0 px helper if its value does not change, one character per line. So the editor builds its form anew each time it opens; never re-attach Carbon form elements.
- `src/vendor/` is generated and committed (the app must work offline and the page has no build step). Carbon's npm packages run IBM telemetry on install unless `IBM_TELEMETRY_DISABLED=true`, which the CI workflow sets.

## User constraints

- Windows only for now.
- No browser extensions, no Obsidian plugins, no launch flags for Chrome/Obsidian; everything must live in the Tauri app.
- Never switch tabs visibly to inspect them.
- Reading browser profile data (Chrome `Sessions/`) and enabling Obsidian's Node inspector (`process._debugProcess`) were blocked by the permission classifier; don't retry without the user's explicit OK.
- Never push to a remote unless asked in that message.

## Findings (don't re-investigate)

- Chromium browsers via UI Automation: every tab's title and Close button are visible, but only the visible pages' URLs. Each visible page's root `Document` has its URL as Value; documents are grandchildren of the `MultiContentsView` pane (two of them in split view, where the address bar only shows one). Split-view tabs are both selected and named "<title> - Left view" / "- Right view". The address bar (class `OmniboxViewViews`) is the fallback. Background tabs have no URL anywhere in UIA. **Tabs are class `Tab` in Chrome/Brave and `EdgeTab` in Edge** (Edge was silently never closing tabs before this was found); windows are class `Chrome_WidgetWin_1` (shared with Electron apps, which have no omnibox).
- **Never search for browser windows with a UI Automation `find_all` on the root element**: it cost 92 ms per pass. A plain `EnumWindows` + class name costs 0.3 ms; then use UI Automation only on the windows found. Creating UI Automation conditions is free, so caching them gains nothing.
- A standard user cannot open a SYSTEM process, not even with `PROCESS_QUERY_LIMITED_INFORMATION`, so the app cannot check who serves the pipe by looking at the process; it asks the pipe for the server's session instead (session 0 = a service). `WTSQueryUserToken` from the service gives the user's limited token, which is what the app should run with.
- A WebView2 app's browser process is shared by every instance using the same user-data folder, so measuring a new instance's processes needs `WEBVIEW2_USER_DATA_FOLDER` set to a fresh folder.
- Obsidian (Electron) exposes no accessibility tree: UIA, MSAA, Chromium's screen-reader honeypot and `SPI_SETSCREENREADER` all failed. Its window title is stale (shows the web viewer's first page).
- Obsidian web viewer content runs in renderers with `--type=renderer --enable-sandbox`; its own UI renderer has `--no-sandbox`. Killing the sandboxed renderer greys the view, but Obsidian then quits cleanly on the next navigation – so the app closes Obsidian via UIA WindowPattern instead.
