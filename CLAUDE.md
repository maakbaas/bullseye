# Bullseye (Tauri tray app, Windows only)

Blocks sites (closes matching Chromium-browser tabs), closes programs by exe name, and closes Obsidian when it shows web content. The user defines three kinds of things, each a list of its own with its own page: **block lists** (what to block: sites, allowed sites, programs, and the enforcers that act on them), **schedules** (when: named weekly schedules; "always" is built in) and **blocks** (what is started: one or more block lists, a schedule or always, and a **lock**: none, a duration, until a date and time, until Windows restarts, a lock schedule (cannot be stopped while a chosen schedule is active; with the block's own schedule that is "locked while active") or a password, kept only as a salted hash). Each block is started and stopped on its own, and several can run at once. A running block is fixed until it ends, and so are the block lists and schedule it uses. Deleting a block list or schedule takes it out of the blocks that use it (none of which may be running): a block left without a block list is deleted, one that loses its schedule is always active, one that loses its lock schedule has no lock (`Library::fallout`, which the delete question spells out). Outside its schedule a running block still runs (and stays locked) but enforces nothing. Definitions and running blocks are held by a **SYSTEM Windows service**; the tray app does the closing. This file is the project's documentation for developers; `CLI.md` is the command line's.

- `src/` – the frontend, built with the **Carbon design system** (see "Design system" below), with no build step: `index.html` (the markup), `app.css` (the page's own layout, in Carbon tokens) and the ES modules in `src/js`: `main.js` (start-up, the router, the tabs, Settings), `core.js` (commands, texts, the status, `ask`, notices), `kinds.js` (`KINDS`), `forms.js` (`LISTS`, `SECTIONS`, the three forms and `weekEditor`), `locks.js` (`LOCKS`), `tiles.js` (the pages of tiles, start / stop, delete), `editor.js` (the editor and its breadcrumb) and `detour.js` (a block list or schedule made from a block). Pages by URL hash, reached from the tabs at the top (Blocks, Block lists, Schedules, Settings): `#/`, `#/lists`, `#/schedules` show each kind as tiles; `/new` and `/edit/<id>` under each (`#/new`, `#/lists/edit/<id>`, …) open its editor (left by Cancel or Save); `#/settings` the unlock password. The three kinds are described once in `KINDS` (title, paths, commands, `held`, a form built by `blockForm` / `listForm` / `scheduleForm`), and pages, tiles and the editor are generic over it. The block list editor and summaries come from `LISTS` and `SECTIONS` (enforcers grouped with the lists they use); a block's lock is set **on its tile**, next to Start (a select from `LOCKS`, saved with the block as it is chosen; a method with settings asks for them first); a schedule's editor is `weekEditor`, a week grid of half hours to drag over (a new schedule starts empty), with the schedule written out under it (`describe_schedule`). The page blocks WebView2's right-click menu (Back, Refresh, …) except in text fields. Every time shown is in words, without units that are zero (`2 hours and 5 seconds`, `1 day, 2 hours and 1 minute`); input stays short (`2h 5m`). **The page has no logic of its own for what the backend knows**: the words come from Rust (`Running::remaining_words` / `schedule_change_words` in the status, the local commands `describe_duration`, `describe_schedule`, `describe_until` and `deletion_fallout` (what deleting a block list or schedule does to its blocks, `Library::fallout`), cached by `described()` where they are shown on tiles), and every action is a command that the CLI sends as the same `Request` through the same `client::Remote`
- `src/strings.js` – **every text the window shows**, in one file for fine-tuning the copy (`window.STRINGS`, nested by page). The page looks them up with `t("path", {placeholders})` (`{n}` picks `one` / `other`); the markup's static texts use `data-t="path"` and `data-t-<attribute>="path"` (`applyStrings`). A new visible text goes there, never inline. Texts from Rust (times in words, schedules, the service's errors) are not in it, so the window and the CLI say the same
- `app-icon.svg` – the app icon: an archery target of five bands of equal width (white, black, blue, red, yellow centre), the source of everything else: `app-icon.png` (1024 px, rendered from it in a browser) and `src-tauri/icons/*` (`npx tauri icon app-icon.png`). Change the SVG, then regenerate both. The icon is not shown in the window (the user found it ugly in the header it had then). It fills its square edge to edge
- `src/vendor/` – Carbon, built by `npm run vendor` (`scripts/vendor-carbon.mjs` from `scripts/carbon/entry.js` and `carbon.scss`) and committed; never edit by hand
- `src-tauri/src/lib.rs` – the shared library: modules, entry modes (`--service`, `--install`, `--uninstall`, otherwise the app), tray, and the page's commands: `block_status`, `save_block` / `delete_block`, `save_list` / `delete_list`, `save_schedule` / `delete_schedule`, `start_block` / `stop_block` and `unlock_all` forward to the service, `describe_schedule` / `describe_duration` / `describe_until` / `deletion_fallout` are local. `main.rs` is the tray exe (`bullseye.exe`, GUI subsystem), `bin/bullseye-cli.rs` the console exe of the CLI. The library is `bullseye_core` (a library and a binary of the same name collide on Windows)
- `src-tauri/src/cli.rs` + `CLI.md` – the command line, `bullseye-cli.exe`: everything the window can do (`status`, `show`, `new`, `edit`, `delete`, `start` (with a lock option, like the tile), `stop`, `list show|new|edit|delete`, `schedule show|new|edit|delete|check`, `unlock`), through the same `client::Remote`. **Keep it level with the window**: a command in `generate_handler!` needs an entry in `cli::GUI_COMMANDS`, a CLI command, a line in the help and in `CLI.md`; a test fails otherwise
- `src-tauri/src/ui.rs` – the window: none at startup, made on a tray click (shown once the page has drawn), its X only hides it, destroyed after 5 minutes hidden (the web view is almost all of the app's memory)
- `src-tauri/src/service.rs` – the running SYSTEM service (service manager, start-up, data folder lock-down); `handler.rs` – what it does with each request (the same code over the pipe and, in debug builds, inside the app); `registration.rs` – installing, locking down (SDDL), starting and removing it
- `src-tauri/src/pipe.rs`, `proto.rs`, `client.rs` – the named pipe `\\.\pipe\bullseye`: server, messages, and the app's side (keeps the last policy in memory; `Remote::local` is the in-process variant)
- `src-tauri/src/definitions.rs` – the `Library`: `BlockList`s, `NamedSchedule`s and blocks (`Definition`: id, name, list ids, schedule id or `None` for always, `lock`), kept in `%ProgramData%\bullseye\blocks.json`. `resolve` looks a block's parts up for starting; `delete_list` / `delete_schedule` take the item out of the blocks that use it (`Library::fallout`). A password lock's password is hashed when saved and never sent back (`Library::redacted`). Each block also keeps the last settings of every other lock method it has had (`kept_locks`, merged by `save_block`; a client's are ignored; a kept lock schedule is no use of that schedule, and deleting the schedule removes it from every block's `kept_locks`), so a method chosen again starts from them, a password as its kept hash. Only today's format is read: Bullseye is installed on clean machines only, with no update path and no migration code
- `src-tauri/src/handler.rs` also holds the sharing rule: a running block, and every block list and schedule it uses, cannot be changed or deleted until it ends (`edit`, under one lock with `start`)
- `src-tauri/src/block.rs` – the running blocks, keyed by definition id: one `Part` per block list (each with its own enforcers and allowed sites), weekly schedule, time zone and its lock (`RunLock`, one variant per lock: when it ends, its lock schedule's week, the start of Windows it waits out, a password's hash; also how `state.json` keeps it; `StartLock` is what starting asks for); locks and schedules are enforced here, never in the UI. `Active` is what the app enforces: every part of every running block that its schedule has active. `is_running()` is "any block exists" (keeps the app alive, refuses updates), also outside its schedule; `locked()` says why one cannot be stopped now (and refuses uninstalling)
- `src-tauri/src/schedule.rs` – `Week`: per weekday (Monday first) spans in minutes `[start, end)`; text form `Mon-Fri 08:00-17:00; Sat 10-12` (`parse` for the CLI, `describe` for the window and the CLI)
- `src-tauri/src/localtime.rs` – local weekday/time for schedules, in the time zone Windows had when the block started (kept in `state.json` as `zone`, since standard users may change the time zone); daylight saving followed
- `src-tauri/src/lock.rs` – lock methods: `none` (stop any time), `duration` (cannot be stopped, ends the block when up), `until` (the same, ending at a local date and time, `2026-10-06 18:00`, read in Windows' time zone when the block starts: `datetime.rs`, `localtime::Zone::instant`), `until_restart` (cannot be stopped, ends when Windows restarts: `boot.rs`; a shut down with Fast Startup is not a restart), `scheduled` (cannot be stopped while its chosen schedule, by id, is active) and `password` (stopped only with its password; the client sends `password`, the service keeps `hash`)
- `src-tauri/src/datetime.rs` – a local date and time (`2026-10-06 18:00`, written out `Tuesday 6 October 2026, 18:00`), platform-free; `localtime::until` is what the window's `describe_until` and the CLI show of an until lock (refused once it has passed)
- `src-tauri/src/boot.rs` – which start of Windows this is: a random id in a volatile registry key (`HKLM\SOFTWARE\bullseye-boot`, HKCU for the debug build's embedded service), gone after a restart; a block locked until restart is not resumed under another id
- `src-tauri/src/duration.rs` – durations: `5s`, `10m`, `3h`, `1d`, combined (`2h 5m`, `1d12h`) or in words; `words()` writes them out
- `src-tauri/src/clock.rs` – internet time (SNTP) that timed blocks are measured against, so moving the Windows clock does nothing
- `src-tauri/src/unlock.rs` – the unlock password, kept only as a salted PBKDF2-SHA256 hash, and the hashing of password locks (`new_hash`, `check_hash`: a random salt each)
- `src-tauri/src/filters.rs` – site lists: plain address prefixes plus `*` (user rejected full uBlock syntax as too complex). Used for the block list and the always-allowed list, which **wins**. Only web pages are matched, never the browser's own pages, so a lone `*` blocks every site and leaves the browser usable
- `src-tauri/src/programs.rs` – programs to close: exe names with `*`, `.exe` added when missing, and a protected list (Windows' own, this app and its CLI, WebView2) that is never closed and refuses entries that would match it
- `src-tauri/src/tab_closer.rs` – 1-second worker in the app doing the closing, as enforcers (`state::Enforcers`, checkboxes in the UI, fixed while a block runs): with the site list, Chromium tabs and split view; with the program list, programs (asked to close, ended after 3 s); without a list, Obsidian's web viewer
- `src-tauri/src/state.rs` – the running blocks on disk (`%ProgramData%\bullseye\state.json`, SYSTEM-owned; each with its `parts`, schedule, zone and locks; only today's format) and the `Enforcers` table (one place to add an enforcer)
- `src-tauri/src/watchdog.rs` – the service's watch over the app (`AppSlot`) and the log writer
- `src-tauri/src/sync.rs` – `locked()` (locks that survive a crash) and `spawn_critical` (a crash in a long-lived thread ends the process, so Windows restarts it)
- `src-tauri/src/setup.rs` + `src-tauri/windows/hooks.nsh` – `--install` / `--uninstall`, run by the NSIS installer (no update path: uninstall first)

**Naming.** The product is **Bullseye** (it was "Site Blocker"). Everything a process or the system goes by is lowercase `bullseye`: the exe (`bullseye.exe`, `mainBinaryName`), the service's key name, the pipe, the data folders (`%ProgramData%\bullseye`, `%LOCALAPPDATA%\bullseye`, `bullseye-dev`), the identifier, safe-mode keys, file and artifact names. Text a person reads is capitalised "Bullseye": the window title, messages and errors, the installer's dialogs, `productName` (so `C:\Program Files\Bullseye` and Settings > Apps) and the service's display name. Development environment variables stay uppercase by convention (`BULLSEYE_SHOW`). So is the Cargo package, and with it the dev build's exe.

## How the pieces keep each other alive

The `bullseye` service runs as SYSTEM, starts at boot, and holds the block definitions, the running blocks, internet time and the unlock hash. The tray app (user session) asks it every second what to enforce, does the closing, and keeps no state; it keeps enforcing the last answer if the service is briefly unreachable.

- The service does not accept a stop request, and its access list (`registration.rs`) gives only SYSTEM stop / change / delete. If it fails by itself, Windows restarts it at once (failure actions).
- The service starts the app at every logon and, **while any block runs** (also outside its schedule), starts it again within ~1 s of it ending. Which process is "the app" is the service's decision: the one it launched, or the installed exe in the console session that registered; never a matter of the process name. An app that has not asked for its policy for 5 s (20 s after starting) during a block is ended and started again, which covers a suspended app. After a sleep the app gets a fresh start instead.
- If the service is not running, the app asks Windows to start it (interactive users may *start* it, nothing more).
- Reboot mid-block: the service reads `state.json` back and resumes every running block with its time left.

**"Unlock"** in the UI (`unlock_all`, password `test1234`, stored only as a hash in `unlock.rs`, which says how to change it) is checked by the service (no slowdown after wrong guesses: PBKDF2 already costs a moment per try). It lives on the Settings page and ends **every** running block (the definitions stay); the app stays open, with nothing to enforce. It is the only way to end a locked block early. `bullseye-cli unlock` does the same. (Unlock used to quit the app too; the user preferred it to stay.)

### Deliberately not hidden

Per the user's decision: nothing here is obscured. The service is called "Bullseye" in the services list (its key name is `bullseye`), the app runs under its own name in Task Manager, it is listed under Settings > Apps, and `%ProgramData%\bullseye\service.log` (administrators can read it) and `%LOCALAPPDATA%\bullseye\app.log` say what happened. The mechanism is friction, not secrecy.

**The honest ceiling** (do not claim otherwise in the UI): an administrator who knows how can run a shell as SYSTEM (for example PsExec `-s`), take ownership of the service object or its data folder and rewrite them, delete the service from the Windows recovery environment, or edit the registry offline. The app is a process of the user it protects against, so someone who can inject code into it can keep it asking for its policy while it enforces nothing. Lock deadlines and schedules are in NTP time; offline, time only advances while the service runs (from `seen` in `state.json`). A running block's time zone is pinned when it starts; an administrator can still rewrite Windows' time zone rules in the registry. Spoofing NTP needs admin. The password hash is in the binary, so a short password can be brute-forced offline. What changed from the old per-user design is the effort: "End task" no longer works.

### Install / remove

`npm run build` makes a **per-machine** NSIS installer (`src-tauri\target\release\bundle\nsis\`), which needs admin and installs to `C:\Program Files\Bullseye` (never a user-writable folder: the exe runs as SYSTEM). Tauri bundles every binary of the package, so `bullseye-cli.exe` lands next to `bullseye.exe` (not on `PATH`). The hooks (`windows/hooks.nsh`) run the app with `--install` (create the service, lock it down, safe-mode keys, start it) and `--uninstall` (the service removes itself, its data and the app). Uninstall is **refused while any block is locked right now** (a duration or until lock, until restart, a lock schedule while it is active, or a password; exit code 2, internet time). If a service is registered but does not answer, the uninstall also stops (exit code 1, nothing removed); with no service registered it carries on. The installer cannot stop the service itself, so it asks over the pipe. `.github/workflows/build.yml` builds the installer as an artifact for every push.

### Recovery: when your own test locks you out

The installed service cannot be stopped by you, by design, and a locked block refuses uninstalling. So test installs in a Windows virtual machine with a snapshot; on a real machine use short blocks (`5s`) and know the unlock password. If it still goes wrong, as an administrator, open a shell as SYSTEM (Sysinternals `psexec -s -i cmd`) and run:

```bat
sc delete bullseye
taskkill /f /im bullseye.exe
reg delete "HKLM\SYSTEM\CurrentControlSet\Control\SafeBoot\Minimal\bullseye" /f
reg delete "HKLM\SYSTEM\CurrentControlSet\Control\SafeBoot\Network\bullseye" /f
rmdir /s /q "%ProgramData%\bullseye"
```

`sc delete` comes first: it marks the service for deletion, so Windows does not start it again when `taskkill` ends the process. Without PsExec, Task Scheduler gives a SYSTEM shell: save those lines as `C:\recover.cmd`, then `schtasks /create /tn recover /sc once /st 00:00 /ru SYSTEM /tr C:\recover.cmd /f`, `schtasks /run /tn recover`, and `schtasks /delete /tn recover /f`. Last resort: the Windows recovery environment's command prompt runs as SYSTEM too.

## Dev workflow

- `npm run dev` needs no service: in a debug build the app runs the service's logic inside itself (`service::embedded`), with its files in `%LOCALAPPDATA%\bullseye-dev`. Kill it at will. `BULLSEYE_USE_SERVICE=1` talks to a real installed service instead. Release builds contain none of this (`debug_assertions`); `cargo check --release` must stay warning-free. The CLI always needs the real service (`cargo run --bin bullseye-cli -- status`).
- There is **no window until you click the tray icon**. Debug aids: `BULLSEYE_SHOW=1` (open at start), `BULLSEYE_REOPEN_AFTER_SECS=n`, `BULLSEYE_UI_TIMEOUT_SECS=n` (shorter keep time).
- Run `npm run dev` as a background task; it rebuilds and relaunches on changes in `src-tauri/`. Changes in `src/` are not picked up automatically – `touch src-tauri/src/main.rs` to force a relaunch.
- Dev log lines contain ANSI colour codes (`Running\e[0m \`target\...`), so patterns like `'Running \`'` never match. Wait for a relaunch by matching `bullseye.exe`, and check the real log text before writing any wait loop.
- Look at UI changes in a browser without Windows: the page's modules do not load from `file://`, so serve `src/` (`python3 -m http.server` in it) and open `index.html` in Playwright's Chromium with a stand-in `window.__TAURI__` (an `addInitScript` that answers the commands from memory); check narrow (~400 px) and wide, light and dark.
- Edit JS/HTML containing escapes (`\n`, regexes) with the Write/Edit tools, not heredocs or Python string replacement – escapes got mangled into literal newlines several times. Syntax-check the page script with `node --check` after edits.
- From Linux, `rustup target add x86_64-pc-windows-msvc` and `cargo clippy --target x86_64-pc-windows-msvc --all-targets` type-check everything (no linking, so no tests); the platform-free modules (`duration`, `schedule`, `lock`) can be tested in a scratch crate via `#[path]`.
- `cargo test` (in `src-tauri/`) runs 119 tests. Ignored on purpose: the network clock, printing a new unlock hash, `the_pipe_answers_like_the_app_expects` (`-- --ignored the_pipe`; no service may be installed, it takes the pipe name) and `a_real_browser_tab_is_closed` (needs a Chromium browser window open on example.com). Also run `cargo clippy --all-targets` (clean), `cargo check --release` and `cargo fmt` (`src-tauri/rustfmt.toml`; CI runs `cargo fmt --check` first).

## Adding an enforcer, a list, a schedule kind or a lock method

The UI is built from tables so these need no new markup:
- **Enforcer**: a field in `state::Enforcers` and a line in `Enforcers::all`; an entry in the right `SECTIONS` group in `src/js/forms.js` (`key` = the field name). If it acts per block, a method on `block::Active` that combines the running blocks (see `blocks_page` / `blocks_program`).
- **List** (inside a block list): see `block::Lists` (a `Uses` variant, `Lists::has`, fields in `definitions::BlockList`, `state::SavedPart`, `block::RunningList`, `proto::Policy`); an entry in `LISTS` and its key in a `SECTIONS` group; an option in `cli::parse_list_changes`.
- **Schedule kind** (other than weekly): a field in `definitions::NamedSchedule` and what it means in `block::Block::in_schedule`; the schedule form in `src/js/forms.js`; the CLI's `schedule new|edit`.
- **Lock method**: a variant of `lock::Lock` (tagged by `method`), what it starts as (`block::StartLock`, from `handler::start`) and runs as (`block::RunLock`, and what it means in `Block::locked`); an entry in `LOCKS` with its `form` (the modal's fields and how to read them, if it has settings), `describe` and `confirm` (what starting asks, or null); an option in `cli::parse_lock`.
- **Anything the window can do**: also in the CLI (see `cli.rs`).

## Design system (Carbon)

All UI uses IBM's **Carbon design system** (https://github.com/carbon-design-system/carbon), through `@carbon/web-components` (`cds-*` elements), `@carbon/styles` and IBM Plex:
- **Follow Carbon's paradigms; don't work around them.** When a request can be met the Carbon way, do it that way, even if a hack would match the request more literally; when it cannot, say so and propose the Carbon-native alternative instead of overriding a component. Never restyle a component's shadow DOM (adopted style sheets, `!important` against its internals); use only its attributes, slots, `::part`s and the theme tokens.
- **Only Carbon components.** Use a `cds-*` component for every control, message and container (buttons, inputs, textareas, checkboxes, selects, tiles, tags, notifications, modals, overflow menus, breadcrumbs, tabs, tooltips). No hand-made controls and no other UI library. A component not yet in the bundle is added to `scripts/carbon/entry.js` (import the specific file, e.g. `.../tag/tag.js`, not the folder's `index.js`) and `npm run vendor` is run; the same goes for icons (`@carbon/icons`, used through `carbonIcon(name, slot)`).
- **Only Carbon tokens.** Colours are `var(--cds-*)` theme tokens, spacing is `var(--cds-spacing-01…13)`, type is Carbon's `cds--type-*` classes in IBM Plex. No hex colours, pixel spacing or other fonts in the page's CSS; `app.css` is layout only.
- **Themes**: `g10` in light mode and `g100` in dark mode, following Windows (the script at the top of `index.html` switches the `cds--g10` / `cds--g100` class on `<html>`). Check both.
- **Responsive**: layout with Carbon's CSS grid (`cds--css-grid`, columns with `cds--css-grid-column cds--sm:col-span-4 cds--md:… cds--lg:…`, and its breakpoints (sm 320, md 672, lg 1056, xlg 1312, max 1584). Put cards straight into the page's grid as columns, so their edges line up with the page header; a nested `cds--subgrid` hangs into the gutters and does not. The block tiles are one per row, full width (`sm:4 md:8 lg:16`), like the empty-state tile, so they resize smoothly with the window; from md up a tile's Start/Stop sits at the right of its row, level with the last summary line (no text under the button). (Carbon allows tiles at any span; its own component for a list of items with status and actions would be a data table, which was not chosen.) The window is resizable down to 360 × 480; every view must work from there up, with no horizontal scrolling. Carbon's `col-span` classes set `display: block`, so a column that is also a flex box needs that restated (see `.block-tile`).
- **Navigation**: no UI shell header (the user removed it: it only repeated the window's title, and Carbon does not require one); the pages are `cds-tabs` in a band at the top (`nav.pages`), on `--cds-layer-01` (white on light, a step up on dark) so menu and content stand apart, sticky while the page scrolls, its tabs from the left edge (`--cds-spacing-05` in), not the content's. As nothing separates it from a Windows 11 title bar (a browser has its tab strip there), the band has a 1 px `--cds-border-subtle` line on top, then `--cds-spacing-04` of room above the tabs, and the same line below (tiles are on layer-01 too and scroll under it). One `cds-tab` per top-level page, an icon before its label (`locked` blocks, `list-checked-16` block lists, `calendar-16` schedules, `settings`; slotted with the label, as Carbon's tabs with icons). Below md (672 px) they are Carbon's icon-only tabs (`main.js` sets `icon-only` on each tab and `icon-size="default"` on the tabs, which lets their tooltips out of the tab bar): square, named by a tooltip and their `aria-label`, so the four fit at 360 px. The router sets the tabs' `value` (`markPage`); an editor, and a block list or schedule made from a block, count as their page's tab. No header links or global actions (those are for tools and panels, not pages), no hamburger, no side nav (folds into a hamburger below 1056 px). A page below a top-level one (the editor) has a `cds-breadcrumb` above its title, built by `setCrumbs`: the page as a link, then the current page (`is-currentpage`), e.g. "Blocks / Work hours"; made from a block it is one deeper, "Blocks / Evening / New block list". Below 672 px Carbon stacks the breadcrumb items; that is by design.
- **Layout**: every view is one full-width column (`sm:4 md:8 lg:16`) in `main`, which is capped at 66rem (Carbon's lg) and centred beyond it. So the content fills the window with Carbon's grid margins until it is 66rem wide, then stays that wide and centred, and every view is exactly as wide as the others. Never give one view's content a narrower width or a `col-start` offset: it makes the views differ and the margins jump at breakpoints.
- **Buttons**: `size="md"` (40 px, the height of a text field) for page and form actions, `size="sm"` inside tiles; not Carbon's default `lg`, which is too big for this app. The editor's Delete is `danger-tertiary` (red outline). The web components' kinds have one dash (`danger-ghost`, `danger-tertiary`), unlike Carbon's CSS classes (`cds--btn--danger--ghost`); an unknown kind silently falls back to the default look.
- **Making things on the way**: the block editor has a New block list and a New schedule button (tertiary). They keep the block as edited so far (`detour`: where to go back, the draft, what to do with the new item), open that kind's editor one level deeper (`#/new/lists/new`, `#/edit/<id>/schedules/new`), and on Save go back to the block with the new item ticked or chosen; Cancel goes back unchanged. Choosing the Schedule lock with no schedule yet asks whether to make one (`#/lock/<id>/schedules/new`), and the lock is set to it once saved; no, and the lock stays as it was. Not a modal: a block list or week grid is a whole page, more than Carbon's modals are for (short tasks).
- **Patterns**: page title `cds--type-productive-heading-05` with a short description; sections `productive-heading-03`; errors and states as `cds-inline-notification` (low contrast) at the top of the view; anything that cannot be taken back asks first in the one `cds-modal` (`ask()` in the script, focus on Cancel via `data-modal-primary-focus`): deleting (`danger`), and starting a block that cannot be stopped (`LOCKS[method].confirm`; a new lock method must say whether it asks). The same modal holds short forms (`ask({fields, read})`, which stays open while `read` gives null and marks the fields with `invalid()`): a lock's settings and the password that stops a password-locked block. The tile itself has only the lock's method select next to Start; choosing a method with settings (`LOCKS[method].form`) opens its form, and Cancel keeps the old lock. The current lock's settings are changed from the tile's ⋮ menu ("Lock settings", hidden for a lock without settings; menu items have no "…"). Each form starts from the block's settings for that method, its lock's or the kept ones (`settingsOf`). The until lock's form is Carbon's date picker (`date-format="Y-m-d"`, so its value and text are ISO) and time picker side by side (`.date-time`). A block tile's summary lines have a 16 px icon in front (`list-checked-16` block lists, `calendar-16` schedule, `locked` / `unlocked` lock, `time` when the schedule turns it on or off): `summaryOf` gives `[icon, text]` lines. A password already set is never known to the window (only its hash is kept), so its fields hold 8 dots (`KEPT`) as a real value of normal colour, not a placeholder, so placeholders keep their own style. Clicking or tabbing into either field clears both; leaving both empty puts the dots back; saving them unchanged keeps the password. The form is not focused on opening, which would clear them. A tile shows a plain `locked` icon (not a button) where its options menu would be while it cannot be changed: a running block, or a block list or schedule a running block uses (which also gets an "In use by a running block" tag).
- **The week grid** (`weekEditor`, `.week` in the page's CSS) is the one hand-made control: Carbon has no calendar or time-grid component and the user asked for a weekly calendar view. It is plain layout coloured with Carbon tokens only and `aria-hidden`. Its hour labels are centred on the lines they name, 00:00 on the top edge to 24:00 on the bottom one (each spans the two half-hour rows above its line and the two below). The user removed the Times text field above it as confusing, so the grid is the window's only way to set a schedule; the CLI's `schedule new|edit --times` is the typed one. If Carbon ever ships a suitable component, use it instead. The one exception to "never touch a component's shadow DOM": text areas side by side (sites to block, always allowed) keep one height when one is resized with its handle (`sameHeight`). `cds-textarea` has no attribute or part for its height, so the same inline height the browser's resize handle set on the dragged one's inner `<textarea>` is set on the others in its row; nothing else is touched. Stacked (narrow window), each keeps its own. The modal's full-width footer buttons are Carbon's design; keep them, with short fixed labels ("Start locked", "Delete"): they have one height, so a label with a time in it runs out of the button. The time goes in the heading and body.
- Web-component quirks: icons go in the `icon` slot (`cds-button`, `cds-overflow-menu`); an overflow menu's icon needs the class `cds--overflow-menu__icon` (without it the icon takes the button's white and vanishes on a light tile); an open `cds-overflow-menu` moves its body out of the host, so listen on the items; read values from the elements (`.value`, `.checked`), whose events are `input` and `cds-checkbox-changed` / `cds-select-selected`. `cds-textarea` sets its helper text's `max-width` from its own measured width, through a ResizeObserver that it disconnects when taken out of the page and makes again only on its next update: a text area moved out of the page and back (a reused form) keeps a 0 px helper if its value does not change, one character per line. So the editor builds its form anew each time it opens; never re-attach Carbon form elements.
- `src/vendor/` is generated and committed (the app must work offline and the page has no build step). Carbon's npm packages run IBM telemetry on install unless `IBM_TELEMETRY_DISABLED=true`, which the CI workflow sets.

## User constraints

- Windows only for now.
- No browser extensions, no Obsidian plugins, no launch flags for Chrome/Obsidian; everything must live in the Tauri app.
- Never switch tabs visibly to inspect them.
- Reading browser profile data (Chrome `Sessions/`) and enabling Obsidian's Node inspector (`process._debugProcess`) were blocked by the permission classifier; don't retry without the user's explicit OK.
- Never push to a remote unless asked in that message.

## Findings (don't re-investigate)

- Chromium browsers via UI Automation: every tab's title and Close button are visible, but only the visible pages' URLs. Each visible page's root `Document` has its URL as Value; documents are grandchildren of the `MultiContentsView` pane (two of them in split view, where the address bar only shows one). Split-view tabs are both selected and named "<title> - Left view" / "- Right view". The address bar (class `OmniboxViewViews`) is the fallback. Background tabs have no URL anywhere in UIA. **Tabs are class `Tab` in Chrome/Brave and `EdgeTab` in Edge** (Edge was silently never closing tabs before this was found); windows are class `Chrome_WidgetWin_1` (shared with Electron apps, which have no omnibox).
- **Never search for browser windows with a UI Automation `find_all` on the root element**: it cost 92 ms per pass. A plain `EnumWindows` + class name costs 0.3 ms; then use UI Automation only on the windows found. Creating UI Automation conditions is free, so caching them gains nothing.
- A standard user cannot open a SYSTEM process, not even with `PROCESS_QUERY_LIMITED_INFORMATION`, so the app cannot check who serves the pipe by looking at the process; it asks the pipe for the server's session instead (session 0 = a service). `WTSQueryUserToken` from the service gives the user's limited token, which is what the app should run with.
- A WebView2 app's browser process is shared by every instance using the same user-data folder, so measuring a new instance's processes needs `WEBVIEW2_USER_DATA_FOLDER` set to a fresh folder.
- Obsidian (Electron) exposes no accessibility tree: UIA, MSAA, Chromium's screen-reader honeypot and `SPI_SETSCREENREADER` all failed. Its window title is stale (shows the web viewer's first page).
- Obsidian web viewer content runs in renderers with `--type=renderer --enable-sandbox`; its own UI renderer has `--no-sandbox`. Killing the sandboxed renderer greys the view, but Obsidian then quits cleanly on the next navigation – so the app closes Obsidian via UIA WindowPattern instead.
